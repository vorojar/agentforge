  @anthropic-ai/sdk 构建带工具调用能力的自定义 AI Agent。

  └───────────────────────┴─────────────────────────────────────────────────┘

  核心流程

  两个 Agent 都实现了相同的循环：
  1. 用户输入 → 加入对话历史
  2. 调用 Claude API
  3. stop_reason === "tool_use" → 执行工具 → 结果送回 → 继续循环
  4. stop_reason === "end_turn" → 输出文本，结束本轮

  几个观察

  - 模型版本：使用 claude-sonnet-4-20250514，README 中列的模型也是当前最新的
  - 工具数据是模拟的：天气数据是 mock 的，只有北京/上海/SF/Tokyo
  四个城市有预设数据

● 这取决于你的业务场景，但我的建议是：统一框架 + 独立配置，不是二选一。

  为什么不要完全统一成一个 Agent

  - 一个 Agent 塞几十个工具，system prompt 又长又杂，Claude
  的工具选择准确率会下降
  - 不同业务的权限、数据源、容错要求差异大，硬塞一起会互相拖累
  - 一个出 bug 全部挂掉

  为什么不要完全独立

  - 每个团队各写一套 Agentic Loop、错误重试、对话管理、日志 — 重复劳动
  - 工具定义格式不统一，后面想互相调用或做编排就很痛苦
  - 运维、监控、计费没法统一管理

  推荐架构：共享内核 + 独立 Agent 实例

  ┌─────────────────────────────────────────────┐
  │              Agent Framework（共享）          │
  │  - Agentic Loop（循环 + stop_reason 处理）    │
  │  - 工具注册/执行机制                          │
  │  - 对话历史管理                               │
  │  - 错误重试 / 限流 / 日志 / 计费              │
  │  - 统一的 Tool 接口约定                       │
  └──────────┬──────────┬──────────┬─────────────┘
             │          │          │
       ┌─────▼──┐ ┌─────▼──┐ ┌────▼───┐
       │ 客服Bot │ │ 数据分析│ │ 审批流  │   ← 独立 Agent 实例
       │        │ │  Agent  │ │ Agent  │
       ├────────┤ ├────────┤ ├────────┤
       │Tools:  │ │ Tools: │ │ Tools: │   ← 各自的工具集
       │ 查工单  │ │ 查SQL  │ │ 读审批  │
       │ 查库存  │ │ 画图表  │ │ 发通知  │
       ├────────┤ ├────────┤ ├────────┤
       │ Prompt │ │ Prompt │ │ Prompt │   ← 各自的 system prompt
       │ Model  │ │ Model  │ │ Model  │   ← 甚至可以选不同模型
       └────────┘ └────────┘ └────────┘

  实际落地的关键

  1. 统一 Tool 接口：所有工具遵循同一个 name + input_schema + execute
  约定（你现在 tools.ts 的模式就可以抽象成这个）
  2. Agent = 配置：一个 Agent 就是 { model, systemPrompt, tools[], maxTokens }
  的组合，创建新 Agent 只需要写配置 + 工具实现
  3. 模型按需选：简单客服用 Haiku 省钱，复杂分析用 Sonnet/Opus
  4. 工具可复用：比如"查用户信息"这个工具，客服和审批都能用，注册一次到处挂载

  简单说：循环机制写一次，业务逻辑各自写。你现在这个项目的结构其实已经有这个雏形
  了 — tools.ts 和 agent.ts 是分开的，只要把 agent 循环再抽象一层就行。
